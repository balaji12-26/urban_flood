# FloodSense — Chennai Relative Flood Risk Index explorer

A hackathon prototype that scores six Chennai zones on a **transparent weighted formula**,
lets you explore how risk shifts under simulated conditions, and shows the provenance of every input.

> Output everywhere is the **Relative Flood Risk Index (0–100)**.
> It is not a flood probability and not a prediction.

## Run

```bash
pip install -r requirements.txt
python run.py
```

Open http://127.0.0.1:5000. Tests:

```bash
python -m pytest -q
```

Set `FLOODSENSE_PORT` to change the port. The app works offline: weather falls back to a
labelled sample, and the frontend falls back to `mock/mock.json` if the API is down.

## Stack

Python 3.11+ / Flask · vanilla HTML + CSS + JS · Leaflet 1.9 · Chart.js 4 · Open-Meteo (no key) · Inter.
No ML. No frameworks.

## How the index works

```
index = 100 × (1 − exp(−Σ(factor_raw × weight) / k))      k = 0.7
weights: rainfall .30 · forecast .20 · water_level .20 · drainage .15 · terrain .10 · history .05
```

| Factor | Label | Source |
|---|---|---|
| Current rainfall | LIVE | Open-Meteo current precipitation, city centroid |
| Forecast 6 h rainfall | FORECAST | Open-Meteo hourly forecast |
| Water level | SIMULATED | Synthetic sensor, deterministic 30 s noise, no real device |
| Terrain risk | DERIVED | SRTM elevation (OpenTopoData), normalised 0–1 |
| Drainage, history | PROFILE | Hand-authored zone characteristics |

Levels: LOW < 30 · MODERATE 30–54 · HIGH 55–74 · CRITICAL ≥ 75.

## Top-bar controls

- **Freeze sensor**: holds the simulated water level at each zone's baseline for stable numbers.
- **Live weather**: off serves cache or the offline fallback without touching the network.
- **Sample storm**: replaces live rainfall with a labelled sample (4.2 mm/h now, 28 mm next 6 h) so
  the rainfall lever has something to scale on a dry day. Never presented as live.

## API

| Route | Purpose |
|---|---|
| `GET /api/zones?live=1&sensor_mode=live\|frozen&weather=sample` | All zones, ranked, with factor breakdown, water-level views, action |
| `GET /api/zones/<id>` | One zone |
| `GET /api/geojson` | Approximate demonstration polygons (with `_disclaimer`) |
| `POST /api/scenario` | `{zone_scenarios:{id:{rainfall_multiplier, drainage_blockage, water_level_rise_cm}}, global:{…}, weights?, k?}` — overrides are local per zone |
| `GET /api/forecast-curve?zone=<id>&rainfall_multiplier=…` | Hour-by-hour projection over the next 6 h |
| `GET /api/validation/{monotone,sensitivity,baseline,replay,all}` | Live validation checks |
| `GET /api/methods` | Methods & Limitations text and constants |

## Guarantees enforced in code

- `compute_risk()` is pure: no randomness, no I/O, no mutated globals (`tests/test_risk_engine.py`).
- All sensor noise lives in `backend/services/sensor_simulator.py`, hash-based, no shared RNG.
- Scenario overrides are local; one zone's scenario never reaches another (`test_zone_independence`).
- Water-level toggle drops the factor from the weighted sum and re-applies `soft_scale`; no renormalisation.
- `WEIGHTS` must sum to 1.0 (assertion in `backend/config.py`).
- SIMULATED data is badged in the map popup, zone panel, simulator, validation and banner.
- Replay always shows the historical-replay disclaimer banner.
